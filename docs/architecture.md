# Design decisions

## Ingestion and chunking

Document identity is collection-local filename; content hashing records versions. Successful re-ingestion transactionally replaces all prior chunks for that filename. Different same-named documents should be renamed before upload. Index signatures reject incompatible embedding/chunk settings; use separate indexes for experiments.

The recursive baseline splits paragraphs and falls back to line/character windows under a tokenizer budget. Structure-aware mode additionally tracks Markdown heading ancestry and preserves fenced code blocks when they fit. Hybrid chunking runs both approaches: structure-aware chunks are retained first, then non-identical recursive fallback chunks are added. Exact duplicates are removed by provenance and content hash, so flat PDFs/text files do not double index size. Oversized blocks are split with overlap. Neither strategy packs adjacent small paragraphs yet; investigate packing as a separate experiment. PDF sections preserve page numbers; Markdown/text chunks preserve line spans. Heading text is included in embeddings when it fits the budget.

## Retrieval

Normalized embeddings enable dot-product cosine search. BM25 uses k1=1.5 and b=0.75 with exact term tokenization preserving identifiers such as X-API-Key. RRF uses one-based rank and k=60. Default retrieval takes 20 from each path, fuses by chunk ID, reranks up to 20, and selects up to seven chunks under the 2,000-token context budget.

Documents receive deterministic local metadata during ingestion: a conservative normalized profile role when recognizable, including compound specialisations such as `fullstack_aiml` separately from `aiml`, plus generic structural section types when an explicit heading is present (for example, `education`, `requirements`, `responsibilities`, `professional_experience`, or `professional_summary`). Compound role wording is atomic: "Full Stack AI/ML" selects `fullstack_aiml`, not standalone `aiml`, unless AIML is separately requested. Common role plurals such as `BDEs` normalize to the same hard profile scope as `BDE`. Explicit role requests such as "only BDE candidates" are applied as a hard document filter before dense search, BM25, fusion, coverage selection, and comparison. A role request with no matching indexed metadata returns no evidence rather than silently widening the scope. Collection-scoped lists, summaries, and comparisons require representation from every in-scope document. An explicit request to differentiate role groups prefers profile-summary evidence and produces cited contrast statements between normalized role groups rather than blending or independently listing the groups. When no role metadata applies, the same route compares the explicitly represented documents as groups, so the behavior is not resume-specific. Section concepts are soft context-selection boosts: education/study/qualification queries prefer a matching education or qualifications section, while employer/work queries prefer work-experience sections; an exact name that uniquely matches one document can scope that boost to its sibling chunks. They never hard-filter unlabelled documents. Summary requests prefer `professional_summary` chunks within the filtered document set. The trace records requested roles, filtered document count, and the final coverage target.

MMR is optional and runs during context selection after reranking. It uses rank-normalized relevance and embedding cosine redundancy. Its effect must be measured rather than assumed positive. Query analysis is currently input validation only; no extra model stage is needed without a tested use case.

The pipeline materializes a deterministic document registry from persisted chunks at retrieval time. Each record carries document type, candidate profile role or job target role, recognized sections, label/title, summary provenance, and bounded skills. It is a replacement-safe projection of the durable chunk store rather than an LLM-generated side table, so it refreshes legacy indexes without re-embedding and works across SQLite and ChromaDB.

## Generation control

An LLM judges evidence sufficiency against the original question. Failure permits at most one rewritten search and another sufficiency grade. The rewritten query changes retrieval only. The initial agent planning call classifies collection-wide, comparative, and aggregation intent in structured fields. Aggregation means the question needs a count, filter, calculation, or comparison over facts from each document. Controller heuristics remain a fallback, and either signal may only broaden evidence coverage; neither can narrow it or bypass the evidence gate. All variants retain evidence gating; corrective=false disables the retry, not the gate. Generation returns structured claims with supplied chunk IDs. Missing or unknown citations cause a visible error. Candidate-comparison requests use a separate structured recommendation result: the model selects a validated document ID, gives criteria and rationale, and the renderer adds one retrieved citation per compared document. This makes the recommendation explicitly an inference from the resumes and prevents a valid comparison from failing merely because the model cited only the selected candidate. Structured aggregation reducers use map/reduce evidence when their pattern is explicit: experience comparisons prefer a cited stated total and otherwise derive a cited, non-overlapping duration from explicit employment date ranges; requested candidate counts are composed with the comparison result. "More than N companies" extracts distinct employment companies per document. Reducers validate full in-scope document coverage and render deterministically; their compact facts do not consume the normal LLM context budget. A bounded event/problem-and-resolution query is also rendered directly when explicit labeled fields such as `Incident`/`Issue`/`Problem` and `Resolution`/`Solution`/`Fix` are both present; root-cause and impact requests remain subject to normal evidence grading. Other questions retain the normal grounded-generation path. Valid IDs are necessary but not sufficient for factual grounding.

## Observability

Each attempt records query, candidate counts, ranked IDs/scores, selected context IDs, evidence verdict/reason, and retrieval duration. Scores depend on the configured stage and are not calibrated answer confidence. UI shows evidence status. Full token accounting, stage-level timing, model revision pinning, and semantic citation validation remain follow-up work.

SQLite document replacement is transactional. ChromaDB uses an upsert followed by stale-record removal because its local API has no multi-operation transaction; the adapter verifies that the final document chunk IDs exactly match the requested replacement and raises an actionable error if they do not. A failed Chroma replacement should be re-indexed rather than assumed complete.
